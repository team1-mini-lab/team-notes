# SRS Template Selection Rationale

## 1. 작성 목적

ISO/IEC/IEEE 29148:2018을 참고한 SRS 템플릿을 선정하고, 미니 React 프로젝트에 적용하기 위해 검토한 기준과 판단 근거를 기록한다.

원본 템플릿의 항목을 그대로 사용하는 대신 LMS 요구사항과 프로젝트 범위를 기준으로 도입, 통합, 간소화, 제외 여부를 결정한다.

## 2. 참고 자료

| 구분 | 자료 | 활용 목적 |
|---|---|---|
| 표준 | [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) | SRS 구성 및 요구사항 작성 원칙 확인 |
| 공개 템플릿 | [DIN-DKE SRS Template](https://github.com/DIN-DKE/ISO_IEC_IEEE_29148__SRS-Template/blob/master/template.md) | SRS 세부 항목 및 문서 구조 비교 |
| 프로젝트 요구사항 | [LMS Requirements](./LMS_REQUIREMENTS.md) | 템플릿 항목의 도입 필요성 판단 |

※ DIN-DKE 공개 템플릿은 저장소 설명에서 ISO/IEC/IEEE 29148:2011을 기반으로 한다고 밝히고 있다. 따라서 2018 표준을 참고 기준으로 삼고, 공개 템플릿은 세부 문서 구조를 검토하기 위한 자료로 활용한다.

## 3. 템플릿 선정 기준

다음 기준으로 공개 템플릿의 항목을 검토한다.

1. LMS R1~R20의 구현 범위를 요구사항으로 명세할 수 있는가?
2. 기능, 품질, 인터페이스, 기술적 제약을 구분할 수 있는가?
3. 요구사항별 검증 방법을 정의할 수 있는가?
4. 요구사항과 구현 작업 및 테스트 간 추적이 가능한가?
5. 프로젝트 규모에 비해 불필요하게 복잡한 항목은 없는가?

## 4. 원본 템플릿 항목 검토

| 원본 항목 | 원본 항목의 의미 | 적용 판단 | 판단 근거 | 최종 반영 항목 |
|---|---|---|---|---|
| Introduction | 문서의 목적, 제품 범위, 용어 및 약어, 참고 자료, 문서 구성을 설명한다. | 도입 | SRS 작성 목적과 미니 React 프로젝트의 범위 및 문서 구성을 정의할 필요가 있다. | 개요 |
| Product Overview | 제품의 개발 배경, 시스템 구성, 주요 기능, 사용자 특성, 전제 조건 및 의존성을 설명한다. 세부 기능 요구사항을 정의하기보다는 요구사항을 이해하기 위한 배경 정보를 제공한다. | 도입·통합 | Phase 1과 Phase 2의 전체 개발 범위 및 주요 기능을 개괄적으로 설명할 필요가 있다. 세부 동작은 FR에서 정의하고 제품 개요에는 중복 작성하지 않는다. | 제품 개요 |
| External Interfaces | 소프트웨어와 사용자 또는 다른 소프트웨어 사이의 입력과 출력, 화면 구성, 데이터 형식 및 인터페이스 특성을 정의한다. | 도입·간소화 | 사용자 인터페이스와 프로젝트에서 필요한 소프트웨어 요소 간 입출력 및 연결 관계를 정의할 필요가 있다. | IR |
| Functional | 입력이나 특정 조건에 따라 소프트웨어가 수행해야 하는 기능과 처리 결과를 정의한다. | 도입 | LMS R1~R16에서 정의한 Virtual DOM, Diff, Patch, History, State, Hooks 등의 기능을 구체적으로 명세할 필요가 있다. | FR |
| Quality of Service | 성능, 보안, 신뢰성, 가용성 등 기능 수행과 관련된 품질 특성을 정의한다. | 도입·간소화 | 프로젝트에서 확인할 성능과 안정성 등 기능 외 품질 기준을 정의할 필요가 있다. | NFR |
| Compliance | 법률, 규정, 표준 및 계약 등에 따라 준수해야 하는 요구사항을 정의한다. 보고서 형식, 데이터 명명 규칙, 감사 기록 등의 내용이 포함된다. | 제외 | 제품 자체에 적용되는 별도의 법규, 인증 또는 규제 준수 요구사항이 정의되어 있지 않다. | - |
| Design and Implementation | 설치, 배포 구조, 유지보수성, 재사용성, 이식성, 비용, 일정 등 설계 및 구현 과정에서 고려해야 하는 제약사항을 정의한다. | 도입·간소화 | LMS R17에 정의된 사용 기술 및 구현 방식의 제약을 요구사항으로 관리할 필요가 있다. 프로젝트에 직접 적용되는 기술적 제약을 중심으로 반영한다. | CON |
| Verification | 소프트웨어가 정의된 요구사항을 충족하는지 확인하기 위한 검증 방법과 절차를 설명한다. 요구사항별로 객관적인 검증 근거를 마련하는 데 목적이 있다. | 도입 | R18~R20의 테스트 요구사항을 반영하고 기능별 검증 기준을 정의할 필요가 있다. 특히 R20은 엣지 케이스를 세부 조건별로 분리하여 검증 항목에 반영한다. | VT |
| Appendixes | 본문을 보충하는 참고 자료, 부가 정보 및 관련 문서를 정리한다. | 도입·간소화 | LMS 요구사항과 SRS 요구사항 및 검증 항목 간의 연결 관계를 확인할 수 있도록 추적성 표를 배치할 필요가 있다. | 추적성 표 |
| Hardware Interfaces | 소프트웨어와 하드웨어 장치 사이의 물리적·논리적 연결 및 데이터와 제어 신호의 교환 방식을 정의한다. External Interfaces의 하위 항목이다. | 제외 | 외부 하드웨어 장치와 연동하는 기능이 프로젝트 범위에 포함되지 않는다. | - |
| Distribution | 조직 내 분산된 시스템, 처리 데이터 또는 제어 장치의 분산 구조와 관련된 제약사항을 정의한다. Design and Implementation의 하위 항목이다. | 제외 | 여러 시스템이나 장치에 걸친 분산 구조를 고려할 요구사항이 없다. | - |
| Cost | 소프트웨어 제품 개발 및 제공에 필요한 금전적 비용을 정의한다. Design and Implementation의 하위 항목이다. | 제외 | 별도의 제품 비용 산정이나 비용 관련 요구사항을 관리할 필요성이 낮다. | - |

※ 원본 템플릿에서 Hardware Interfaces는 External Interfaces의 하위 항목이며, Distribution과 Cost는 Design and Implementation의 하위 항목이다.

※ Product Overview는 시스템의 배경과 주요 기능을 개괄적으로 설명하는 항목이다. 세부적인 기능 동작과 조건은 Functional에서 정의한다.

※ 위 판단은 프로젝트 범위에 따른 적용 방안이며, 표준이나 공개 템플릿에서 해당 항목을 반드시 제외하도록 규정한다는 의미는 아니다.

## 5. LMS 요구사항과 SRS 항목의 대응

| LMS 요구사항 | 요구사항 성격 | SRS 반영 항목 |
|---|---|---|
| R1~R16 | Phase 1 및 Phase 2 기능 구현 | FR, 관련 인터페이스 요구사항은 IR |
| R17 | 기술 및 구현 제약 | CON |
| R18 | 단위 테스트 | VT |
| R19 | 통합 및 기능 테스트 | VT |
| R20 | 엣지 케이스 검증 | VT |

NFR은 개별 LMS 요구사항에만 대응시키는 것이 아니라 프로젝트 전체에 적용할 성능 및 품질 기준을 별도로 정의한다.

### 5.1 R20 엣지 케이스 검증 항목 분리

R20의 엣지 케이스 검증은 하나의 테스트로 처리하지 않고, 입력 구조와 변경 상황 및 History 상태에 따라 세부 검증 항목으로 분리한다.

| 구분 | 검증 대상 | 확인할 내용 |
|---|---|---|
| R20-1 | 다양한 HTML 태그 및 요소 | 서로 다른 태그와 요소 구조에서도 Virtual DOM 변환 및 렌더링이 정상적으로 수행되는가? |
| R20-2 | 변경 사항이 없는 경우 | 이전 Virtual DOM과 새로운 Virtual DOM이 동일할 때 불필요한 DOM 변경이 발생하지 않는가? |
| R20-3 | 요소 추가 및 삭제 | 요소가 추가되거나 삭제되었을 때 변경 사항이 올바르게 반영되는가? |
| R20-4 | 속성 변경 | 요소의 속성이 변경되었을 때 변경 사항이 올바르게 반영되는가? |
| R20-5 | 빈 노드 | 자식 노드가 없거나 내용이 비어 있는 경우에도 정상적으로 처리되는가? |
| R20-6 | History 경계 조건 | 되돌리기 또는 다시 실행할 이전·다음 기록이 없을 때 오류 없이 처리되는가? |

각 검증 항목은 VT에 개별 테스트로 연결하여 검증 결과를 확인할 수 있도록 구성한다.

※ R20-1~R20-6은 검증 범위를 구체화하기 위한 분해안이다. 최종 검증 항목과 VT 번호는 LMS R20 원문 및 실제 구현 범위와 대조하여 확정한다.

## 6. 최종 결정

- ISO/IEC/IEEE 29148:2018을 SRS 작성의 참고 표준으로 선정한다.
- DIN-DKE 공개 SRS 템플릿을 세부 항목 및 문서 구조 검토 자료로 사용한다.
- LMS R1~R20을 기준으로 필요한 항목을 선정하고 프로젝트 규모에 맞게 조정한다.
- Product Overview는 시스템의 전체 구성과 주요 기능을 개괄적으로 설명하고, 세부 기능은 FR에서 정의한다.
- FR, NFR, IR, CON, VT로 요구사항을 구분한다.
- R20의 엣지 케이스를 세부 검증 조건별로 분리하여 VT에 반영한다.
- LMS 요구사항부터 SRS 및 검증 항목까지 추적할 수 있도록 구성한다.
