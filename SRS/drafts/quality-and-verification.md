# Quality, Interface, Constraints and Verification

> 작성 담당: C  
> 작성 범위: SRS 3.2, 3.3, 3.4, 4, 5.1  
> 문서 상태: Draft

## 1. Non-functional Requirements (SRS 3.2)

시스템의 성능, 안정성, 유지보수성 등 품질 요구사항을 작성한다.

| 요구사항 ID | 품질 특성 | 요구사항 내용 | 측정 및 검증 기준 |
|---|---|---|---|
| NFR-01 | Performance | 시스템은 DOM 변경 시 변경되지 않은 영역에 대한 불필요한 업데이트를 최소화해야 한다. | 변경된 노드와 유지된 노드 비교 |
| NFR-02 | Reliability | 시스템은 정의된 입력 조건에서 각 기능을 정상적으로 수행해야 한다. | 정상 입력 및 예외 입력 테스트 |
| NFR-03 | Maintainability | 시스템은 Virtual DOM, Diff, Patch, Component, Hooks 기능을 역할에 따라 구분하여 관리해야 한다. | 모듈별 책임 및 인터페이스 검토 |

### 추가 확인 사항

| 항목 | 결정할 내용 |
|---|---|
| 성능 목표 | 렌더링 및 Diff 처리 시간의 측정 여부와 목표값 |
| 안정성 | 빈 값, 잘못된 입력, 경계 조건의 처리 범위 |
| 유지보수성 | 모듈 분리 및 함수별 책임 범위 |

## 2. Interface Requirements (SRS 3.3)

사용자 인터페이스와 모듈 간 인터페이스 요구사항을 작성한다.

| 인터페이스 ID | 인터페이스 대상 | 요구사항 내용 | 입력 | 출력 |
|---|---|---|---|---|
| IR-01 | 테스트 영역 | 사용자는 테스트를 위한 HTML 내용을 입력하거나 수정할 수 있어야 한다. | HTML 입력값 | 입력된 테스트 내용 |
| IR-02 | Patch 버튼 | 사용자는 Patch 기능을 실행할 수 있어야 한다. | 버튼 클릭 | 변경 사항 적용 |
| IR-03 | Undo/Redo 버튼 | 사용자는 변경 이력을 되돌리거나 다시 적용할 수 있어야 한다. | 버튼 클릭 | 이전 또는 이후 상태 |
| IR-04 | DOM 변환 모듈 | 모듈은 DOM 노드를 전달받아 Virtual DOM 객체를 반환해야 한다. | DOM 노드 | Virtual DOM 객체 |
| IR-05 | Diff 모듈 | 모듈은 이전·새로운 Virtual DOM을 전달받아 변경 사항을 반환해야 한다. | 두 Virtual DOM | Diff 결과 |
| IR-06 | Patch 모듈 | 모듈은 Diff 결과를 전달받아 실제 DOM에 변경 사항을 적용해야 한다. | Diff 결과 및 실제 DOM | 변경된 DOM |

> 내부 모듈의 함수명, 매개변수 및 반환 형식은 설계 문서에서 확정한다.

## 3. Constraints (SRS 3.4)

프로젝트 구현에 적용되는 기술적 제약사항과 전제조건을 작성한다.

| 제약사항 ID | 구분 | 제약 조건 | 사유 |
|---|---|---|---|
| CON-01 | 기술적 제약 | React, Vue 등 기존 UI 프레임워크를 사용하지 않고 핵심 기능을 직접 구현한다. | 과제 목적 |
| CON-02 | 개발 환경 | Vanilla JavaScript 또는 TypeScript와 HTML/CSS를 기반으로 구현한다. | 과제 개발 환경 |
| CON-03 | 구현 범위 | Phase 1의 Virtual DOM, Diff, Patch와 Phase 2의 Function Component, Hooks를 구현한다. | 과제 요구사항 |
| CON-04 | 전제조건 및 의존성 | 브라우저 DOM API를 사용할 수 있는 환경에서 실행한다. | 웹 애플리케이션 실행 환경 |

## 4. Verification (SRS 4)

요구사항별 구현 여부를 확인하기 위한 검증 방법과 통과 기준을 작성한다.

### 4.1 검증 방법

| 검증 방법 | 설명 |
|---|---|
| Unit Test | 개별 함수 또는 모듈의 입력과 출력 검증 |
| Integration Test | 여러 모듈 간 연동 검증 |
| Functional Test | 사용자의 조작에 따른 전체 기능 동작 검증 |
| Boundary Test | 빈 값, 잘못된 입력, 경계 조건에서의 동작 검증 |

### 4.2 요구사항 검증표

| 검증 ID | 요구사항 ID | 검증 방법 | 테스트 조건 | 예상 결과 | 합격 기준 |
|---|---|---|---|---|---|
| VT-01 | FR-01 | Unit Test | DOM 요소를 Virtual DOM으로 변환 | Virtual DOM 객체 생성 | 원본 DOM의 노드 구조와 대응 |
| VT-02 | FR-03 | Unit Test | 두 Virtual DOM 비교 | 변경 사항 탐지 | 예상한 Diff 결과와 일치 |
| VT-03 | FR-06 | Integration Test | Diff 결과를 Patch에 전달 | 실제 DOM 업데이트 | 실제 DOM에 변경 사항 반영 |
| VT-04 | FR-09 | Functional Test | Undo 실행 | 이전 상태 복원 | 변경 전 상태와 일치 |
| VT-05 | FR-14 | Functional Test | 컴포넌트 상태 변경 | 컴포넌트 재렌더링 | 변경된 상태가 UI에 반영 |
| VT-06 | FR-19 | Unit Test | useEffect 의존성 변경 | Effect 실행 여부 판단 | 정의한 의존성 조건과 일치 |

> 검증 ID와 요구사항 ID는 A, B 담당자가 확정한 요구사항 목록에 맞춰 최종 정리한다.

## 5. Requirements Traceability (SRS 5.1)

기존 과제 요구사항과 SRS 요구사항, 검증 항목 간의 추적 관계를 작성한다.

| 원본 요구사항 ID | SRS 요구사항 ID | 검증 ID | 비고 |
|---|---|---|---|
| R1 | FR-01 | VT-01 | 확인 필요 |
| R2 | FR-03 | VT-02 | 확인 필요 |
| R3 | FR-06 | VT-03 | 확인 필요 |
| R4 | FR-14 | VT-05 | 확인 필요 |

> 위 매핑은 형식 예시다. 기존 R1~R20의 실제 내용을 확인한 뒤 연결한다. 하나의 원본 요구사항이 여러 SRS 요구사항으로 분리될 수도 있다.
