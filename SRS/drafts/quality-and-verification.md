## 1. Non-functional Requirements (SRS 3.2)

시스템의 성능, 안정성, 유지보수성 등 품질 요구사항을 작성한다.

| 요구사항 ID | 품질 특성 | 요구사항 내용 | 측정 및 검증 기준 | 관련 PR ID |
|---|---|---|---|---|
| NFR-01 | Performance | 시스템은 DOM 변경 시 변경되지 않은 영역에 대한 불필요한 업데이트를 최소화해야 한다. | 변경된 노드와 유지된 노드 비교 | PR-02, PR-06, PR-15 |
| NFR-02 | Reliability | 시스템은 정의된 입력 조건에서 각 기능을 정상적으로 수행해야 한다. | 정상 입력 및 예외 입력 테스트 | PR-18, PR-19, PR-20 |
| NFR-03 | Maintainability | 시스템은 Virtual DOM, Diff, Patch, Component, Hooks 기능을 역할에 따라 구분하여 관리해야 한다. | 모듈별 책임 및 인터페이스 검토 | PR-18 |

### 추가 확인 사항

| 항목 | 결정할 내용 |
|---|---|
| 성능 목표 | 렌더링 및 Diff 처리 시간의 측정 여부와 목표값 |
| 안정성 | 빈 값, 잘못된 입력, 경계 조건의 처리 범위 |
| 유지보수성 | 모듈 분리 및 함수별 책임 범위 |

## 2. Interface Requirements (SRS 3.3)

사용자 인터페이스와 모듈 간 인터페이스 요구사항을 작성한다.

| 인터페이스 ID | 인터페이스 대상 | 요구사항 내용 | 입력 | 출력 | 관련 PR ID |
|---|---|---|---|---|---|
| IR-01 | 테스트 영역 | 사용자는 테스트를 위한 HTML 내용을 입력하거나 수정할 수 있어야 한다. | HTML 입력값 | 입력된 테스트 내용 | PR-03, PR-05 |
| IR-02 | Patch 버튼 | 사용자는 Patch 기능을 실행할 수 있어야 한다. | 버튼 클릭 | 변경 사항 적용 | PR-03, PR-06 |
| IR-03 | Undo/Redo 버튼 | 사용자는 변경 이력을 되돌리거나 다시 적용할 수 있어야 한다. | 버튼 클릭 | 이전 또는 이후 상태 | PR-03, PR-07 |
| IR-04 | DOM 변환 모듈 | 모듈은 DOM 노드를 전달받아 Virtual DOM 객체를 반환해야 한다. | DOM 노드 | Virtual DOM 객체 | PR-01 |
| IR-05 | Diff 모듈 | 모듈은 이전·새로운 Virtual DOM을 전달받아 변경 사항을 반환해야 한다. | 두 Virtual DOM | Diff 결과 | PR-02 |
| IR-06 | Patch 모듈 | 모듈은 Diff 결과를 전달받아 실제 DOM에 변경 사항을 적용해야 한다. | Diff 결과 및 실제 DOM | 변경된 DOM | PR-06 |
| IR-07 | Phase 2 테스트 페이지 | 사용자는 입력 및 클릭을 통해 State 변경과 화면 갱신을 확인할 수 있어야 한다. | 사용자 입력 및 클릭 | 변경된 UI | PR-16 |
| IR-08 | State 변경 인터페이스 | 컴포넌트는 상태 변경 함수를 통해 State 변경을 요청할 수 있어야 한다. | 상태 변경 함수 호출 | 변경된 State 및 화면 갱신 | PR-12 |

> 내부 모듈의 함수명, 매개변수 및 반환 형식은 설계 문서에서 확정한다.

## 3. Constraints (SRS 3.4)

프로젝트 구현에 적용되는 기술적 제약사항과 전제조건을 작성한다.

| 제약사항 ID | 구분 | 제약 조건 | 사유 | 관련 PR ID |
|---|---|---|---|---|
| CON-01 | 기술적 제약 | React, Vue 등 기존 UI 프레임워크를 사용하지 않고 핵심 기능을 직접 구현한다. | 과제 목적 | PR-17 |
| CON-02 | 개발 환경 | Vanilla JavaScript 또는 TypeScript와 HTML/CSS를 기반으로 구현한다. | 과제 개발 환경 | PR-17 |
| CON-03 | 구현 범위 | Phase 1의 Virtual DOM, Diff, Patch와 Phase 2의 Function Component, Hooks 및 Batching을 구현한다. | 과제 및 팀 합의 사항 | PR-01~PR-16, PR-21 |
| CON-04 | 전제조건 및 의존성 | 브라우저 DOM API를 사용할 수 있는 환경에서 실행한다. | 웹 애플리케이션 실행 환경 | PR-01, PR-04 |

## 4. Verification (SRS 4)

요구사항별 구현 여부를 확인하기 위한 검증 방법과 통과 기준을 작성한다.

### 4.1 검증 방법

| 검증 방법 | 설명 |
|---|---|
| Unit Test | 개별 함수 또는 모듈의 입력과 출력 검증 |
| Integration Test | 여러 모듈 간 연동 검증 |
| Functional Test | 사용자의 조작에 따른 전체 기능 동작 검증 |
| Boundary Test | 빈 값, 잘못된 입력, 경계 조건에서의 동작 검증 |

### 4.2 Phase 1 검증 항목

| 검증 ID | 요구사항 ID | 검증 방법 | 테스트 조건 | 예상 결과 | 합격 기준 |
